# FE 프로젝트 AI 개발 환경·구조 전체 점검 지시서

이 FE 프로젝트의 AI 개발 환경(하네스, AI 전담 운영 방식), 디자인 시스템 적용 상태,
코드 구조를 전체 점검하고 더 나은 구조가 있는지 분석한다.
목표는 "바로 고치기"가 아니라 **"내가 결정할 수 있는 점검 보고서와 개선 제안서"**를 만드는 것이다.
속도보다 깊이와 정확성이 중요하다.

작업 중 맥락이 흐려지면 언제든 이 파일(docs/ai-audit/TASK.md)을 다시 읽고 이어서 진행한다.

---

## 배경

- 이 프로젝트는 백엔드 개발자가 FE 경험을 쌓기 위해 진행하며, **FE 코드는 AI가 100% 작성**하고
  사람은 핵심 학습 포인트만 짚는 방식으로 운영 중이다.
- 이 운영 방식 자체가 잘 작동하는 구조인지도 점검 대상이다.

---

## 규칙

- **기존 코드와 설정은 수정하지 않는다.** 모든 산출물은 `docs/ai-audit/` 하위에만 만든다.
  (기존 `CLAUDE.md`, `.claude/`, `docs/` 등도 수정 금지. 개선안은 제안서와 예시로만 제시)
- 질문하지 않는다. 판단이 필요한 사항은 `docs/ai-audit/decisions-needed.md`에
  선택지, 장단점, 추천을 적고 진행한다.
- 모든 지적과 제안에는 실제 파일 경로·코드 인용을 근거로 붙인다.
- 외부 자료를 참고한 주장에는 출처 URL을 붙인다.
- 이 레포는 공개될 수 있다. 산출물에 비밀값, 내부 URL, 개인정보를 적지 않는다.
- `.gitignore`로 제외된 파일(예: `docs/private/`)은 이 환경에 없을 수 있다.
  참조는 되는데 파일이 없으면 "확인 불가"로 기록하고 추측하지 않는다.
- 빌드·실행 환경 문제로 30분 이상 막히면 `docs/ai-audit/blockers.md`에 정리하고
  분석 가능한 범위까지 진행한다.

## 1단계: 계획

`docs/ai-audit/checklist.json`을 아래 형식으로 만들고, 2~8단계 산출물을 항목으로 등록한다.

```json
{
  "items": [
    {
      "id": "ai-setup",
      "artifact": "docs/ai-audit/01-ai-setup.md",
      "done": false,
      "review_rounds": 0,
      "rubric_scores": {}
    }
  ]
}
```

---

## 2단계: 실행 가능 상태 확인 → `docs/ai-audit/00-baseline.md`

- 의존성 설치, 빌드, lint, 타입체크, 테스트를 실행하고 결과를 기록한다.
- 가능하면 개발 서버를 띄우고 Playwright로 주요 화면 스크린샷을 `docs/ai-audit/screenshots/`에 저장한다.
  브라우저 설치나 실행이 불가하면 이 부분은 건너뛰고 사유를 기록한다.

---

## 3단계: AI 개발 환경 점검 → `docs/ai-audit/01-ai-setup.md`

- 인벤토리: `CLAUDE.md`(모든 위치), `.claude/`(settings, hooks, skills, commands, agents),
  `.mcp.json`, 하네스 관련 파일(feature list, progress, plan 문서 등), AI용 문서 구조
- 각 요소가 실제로 무엇을 하는지, 서로 중복·충돌·누락이 없는지 분석
- 규칙이 실제 코드에서 지켜지고 있는지 샘플링 검증 (지시 vs 실제 결과의 차이)
- "AI 100% 전담 + 학습 포인트만 사람이 짚기" 운영 방식 평가
  - 사람의 검토 지점이 어디에 있고, 빠진 곳은 없는가
  - 학습 포인트가 실제로 남고 있는가 (문서, 커밋, 주석 등)
  - AI가 잘못된 방향으로 갔을 때 감지할 장치가 있는가

---

## 4단계: 디자인 시스템 점검 → `docs/ai-audit/02-design-system.md`

- 디자인 토큰(색상, 타이포, 간격, radius, shadow 등)의 정의 위치와 구조
- 토큰 사용률: 하드코딩된 색상·간격·폰트 크기를 검색해 위반 목록과 비율 산출
- 공통 컴포넌트 목록, 사용 현황, 같은 역할의 컴포넌트 중복 여부
- 다크모드, 반응형, 접근성(대비, 포커스, aria) 처리 상태
- AI가 디자인 시스템을 지키도록 하는 장치(문서, lint 규칙, 예시)가 있는지
- 스크린샷이 있다면 화면 간 시각적 일관성도 평가

---

## 5단계: 코드 구조 점검 → `docs/ai-audit/03-code-structure.md`

- 폴더 구조, 라우팅, 상태 관리, API 호출 계층, 인증 처리, 에러 처리, 테스트 구성
- 의존 방향과 레이어 경계 (Mermaid 다이어그램 포함)
- 일관성이 깨진 지점과 기술 부채 목록 (심각도 표시)

---

## 6단계: 리서치 → `docs/ai-audit/04-research.md`

- Claude Code 공식 문서 기준 권장 설정(CLAUDE.md 작성법, hooks, skills, subagents)과
  장시간 에이전트 하네스 패턴
- 사용 중인 FE 스택의 권장 프로젝트 구조와 디자인 시스템 운영 사례
- 각 접근법을 이 프로젝트에 적용했을 때의 적합성 평가

---

## 7단계: 개선 제안서 → `docs/ai-audit/05-proposals.md` + `docs/ai-audit/examples/`

- 영역별(AI 환경, 디자인 시스템, 코드 구조)로 선택지 2~3개, 장단점, 작업량, 추천안
- 우선순위 로드맵: "지금 당장 / 다음 기능 개발 전 / 여유 있을 때"로 구분
- `examples/`에 추천안 기준 개선 예시 작성
  - 개선된 `CLAUDE.md` 초안
  - 개선된 `.claude/` 구성 예시 (hooks, skills 등)
  - 디자인 토큰 위반을 잡는 lint 규칙 예시
  - 컴포넌트 하나의 Before / After

---

## 8단계: 독립 리뷰 루프 (가장 중요)

다음 5개 산출물 각각에 대해 리뷰 루프를 수행한다.

- `01-ai-setup.md`
- `02-design-system.md`
- `03-code-structure.md`
- `05-proposals.md`
- `examples/`

각 산출물마다:

1. 서브에이전트를 새로 띄워 **"이 보고서를 승인하기 전에 반드시 문제를 찾아내는
   까다로운 시니어 FE 엔지니어이자 AI 개발 워크플로 전문가"** 역할로 리뷰시킨다.
   평가 기준(rubric), 각 1~5점:
   - **근거성**: 지적마다 실제 파일·코드나 출처가 있는가
   - **구체성**: 바로 실행 가능한 수준인가
   - **일관성**: 다른 문서와 모순이 없는가
   - **판단 가능성**: 사람이 읽고 결정을 내릴 수 있는가
2. 리뷰 결과를 `docs/ai-audit/reviews/<문서명>-round-<N>.md`로 저장한다.
3. 지적 사항을 반영해 수정하고 커밋한다.
4. **모든 항목 4점 이상, 최소 2라운드**를 거칠 때까지 반복한다. (최대 4라운드)
5. `checklist.json`에 `review_rounds`와 `rubric_scores`를 기록한다.

## 9단계: 마무리

- 전체 문서 간 일관성 최종 점검
- `docs/ai-audit/decisions-needed.md`
  - 결정 항목을 중요도 순으로, 각 항목에 추천안과 "결정하면 바로 시작할 수 있는 다음 작업" 포함
- `docs/ai-audit/README.md`
  - 한 페이지 요약: 핵심 발견 5개, 가장 먼저 할 일 3개, 문서 읽는 순서
- 작업 시작·종료 시각과 단계별 소요 시간을 `date` 명령 기준으로 README에 기록

## 완료 기준

- `checklist.json` 전 항목 `done=true`, 리뷰 대상 문서 rubric 4점 이상
- `docs/ai-audit/reviews/`에 리뷰 파일 최소 10개
- 기존 코드·설정 변경 없음 (`git diff`로 `docs/ai-audit/` 외 변경이 없는지 확인)
- 단계마다 커밋하고, 마지막에 작업 브랜치를 push하고 PR을 생성한다.
  PR 본문에는 README 요약과 리뷰 라운드별 주요 개선 사항을 정리한다.
